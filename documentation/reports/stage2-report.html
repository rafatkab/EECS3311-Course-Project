Stage 2 Implementation Report

AI-powered Study Planner | EECS 3311 | Rafat Kabir
Progress draft: F01–F03, November 1, 2026.

1. Overview and status

Students can create courses, upload materials, and generate document summaries through a Vaadin GUI or Java CLI. Spring Boot stores courses, materials, and summaries in H2. F03 uses local Ollama; the HTTP adapter also supports hosted OpenAI-compatible providers.

F01–F03 are implemented. Editing/deletion and F04–F10 remain pending. Authentication supports one locally configured account and does not count as a project feature.

2. Feature-to-implementation mapping

F01: Course Creation. Deterministic. References: Stage 1 Task 1.2 F01, UC-01, SD01, and Task 4 F01. Students enter a name, description, start date, and end date. The system validates the input, saves an owned course, and displays it on the dashboard. Video: pending.

PartFiles, responsibilities, and key methods
GUIfrontend/.../views/MainView.java: showSignIn, showDashboard, openCourseForm, refreshCourses, and renderCourses handle sign-in, forms, errors, and course cards. themes/study-planner/styles.css styles the UI.
API clientfrontend/.../course/CourseApi.java: createCourse/viewCourses call the backend. CourseApiFactory.connect creates a client for each signed-in view. Frontend Course and CreateCourseRequest records carry API data.
REST APIbackend/.../course/CourseController.java: createCourse, viewCourses, and getCourse expose POST/GET /api/courses and GET /api/courses/{id}.
Application and domainCourseService coordinates creation and retrieval. User.createCourse/viewCourses create and retrieve owned courses. Backend Course validates domain data; CreateCourseRequest validates API fields.
StorageCourseRepository defines storage operations. JdbcCourseRepository.save/findByOwner/findByIdAndOwner use SQL. schema.sql defines the table. H2 files persist under backend/data/.
Authentication and errorsSecurityConfiguration verifies credentials; CsrfController.token supports protected writes. ApiExceptionHandler handles invalid requests and storage failures. The authenticated student determines course ownership.
CLIcli/StudyPlannerCli.java: main/run provide create, list, and help using the same authenticated API.

Flow: form or CLI → CourseController → CourseService → User.createCourse → CourseRepository → H2. The GUI then reloads the saved course list. Failed submissions show errors and preserve form input.

All four fields are required. Names allow 120 characters; descriptions allow 2000. Text is trimmed, and end dates must be on or after start dates. Same-day courses and duplicate names are allowed. Course queries are restricted to their owner.

F02: Upload Learning Materials. References: Stage 1 Task 1.2 F02, UC-02, SD01, and Task 4 F02. Open an owned course, select files, and view the saved materials and extracted text. Upload/validation/text extraction are deterministic; the planned AI processing belongs to later features. Video: pending.

PartImplementation and key methods
GUI / clientMainView.openCourse opens CourseMaterialsPanel; upload, refreshMaterials, and viewText show results and errors. Each file offers View text and Download original. CourseApi.uploadMaterial/listMaterials/materialContent/downloadMaterial call the authenticated API.
API / serviceCourseController.uploadMaterial/listMaterials/materialContent/downloadMaterial delegate to MaterialService, which verifies course ownership before access.
Domain / parsingCourse.addMaterial creates LearningMaterial; getContent exposes extracted text. MaterialParser.parse checks filenames and parses PDF, DOCX, or UTF-8 TXT using PDFBox, POI, or UTF-8 decoding.
Storage / CLIMaterialRepository and JdbcMaterialRepository save metadata, original BLOB, and extracted text together. StudyPlannerCli adds upload, materials, and content.

Rules: up to 10 files, 10 MiB each; unsupported, empty, corrupt, encrypted, or text-free files are rejected. No OCR is provided. Text is limited to 1,000,000 characters, PDF to 500 pages, and expanded DOCX to 20 MiB/1000 entries. API batches roll back on any failure; GUI files upload independently. Originals and text survive restarts.

F03: Document Summarization. AI-based. References: Stage 1 F03, UC-03, SD02 summary branch, and Task 4 F03. Select Summarize document; the agent summarizes source sections, synthesizes them when needed, resolves selected source-excerpt IDs to verified quotations, and saves the result. View saved summary reuses it; regeneration explicitly requests a replacement. CLI: summarize, summary, regenerate-summary. Video pending.

PartImplementation
GUI / APIfrontend/.../views/SummaryActions runs background requests; CourseApi.summarize/viewSummary call backend/.../resource/SummaryController. Progress and safe errors remain visible while inference runs.
Agent / resourceCourse.generateStudyResource calls StudyAssistantFacade.summarize. ContentAgent.summarize plans sections and validates responses from AIEngine.generate. StudyResourceFactory.createResource constructs Summary, extending StudyResource; view returns its text.
StorageSummaryService verifies ownership, guards concurrent generation, and checks the source hash. SummaryRepository/JdbcSummaryRepository save the latest summary, evidence, model, and usage. Failed regeneration preserves the previous result.

F03 accepts 40–32,000 source characters. Generation has schema-constrained output, bounded calls/time, and one repair attempt for invalid results. Missing setup, provider failures, insufficient text, invalid output, and timeouts return errors without saving. Quotations must match the source; factual accuracy still needs human review.

6. Development and verification

Twenty-five backend tests and the production frontend build pass. Coverage includes F01/F02 regression, F03 ownership/CSRF, section planning, output repair, quotation checks, cache/regeneration, timeouts, provider errors, and concurrent generation. Scripted-provider Chrome/CLI checks pass for summary progress, dialogs, saved results, regeneration, errors, mobile layout, and persistence. These fixtures test integration, not model quality. Real qwen2.5:1.5b verification also passed: CLI generation, browser viewing/regeneration, and a two-section document synthesized in three model calls. Source quotations were checked and the sample output reviewed. This verifies a working local integration, not general model accuracy.

Checks: backend/mvnw.cmd clean verify, frontend mvnw.cmd package -Pproduction, and scripts/verify-f01.ps1. Runtime checks use isolated test data and stop their own servers. A missing BCrypt encoding prefix was found and corrected during testing.

F02 runtime checks use scripts/verify-f01.ps1 -IncludeF02. Real-client checks caught a text-preview Accept-header mismatch and a parallel-upload CSRF session race. Correct response headers and serialized token/write requests fixed them.

Live testing exposed paraphrased quotations and missing JSON fields in the small model; constrained output and indexed evidence corrected these failures. F03 checks: scripts/verify-f01.ps1 -IncludeF03 uses a test-only provider; scripts/verify-f03-live.ps1 uses real Ollama and a safe lecture sample. No production fake-response fallback exists.
