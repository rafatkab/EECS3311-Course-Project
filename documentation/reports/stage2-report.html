1. Project overview and implementation status

The application helps students organize courses and eventually generate personalized study resources and plans. The current increment implements course creation and an owned-course dashboard. A Vaadin Flow Java UI runs in frontend/; a separate Spring Boot REST application runs in backend/. A Java 17 source-file CLI calls the same REST API. JDBC writes courses to a file-backed H2 database, so saved courses survive backend restarts.

The Stage 1 references are Task 1.2 F01, Task 2.2 UC-01, Tasks 3/4 F01, the Course/User UML classes, and SD01. The Stage 2 assignment requires traceability, GUI and CLI, ten meaningful features, five distinct meaningful course design patterns, an LLM with agent behavior, ongoing code commits, a PDF/Word report, demonstrations, and local-only credentials. Only the supplied Stage 1 report and Stage 2 instructions were available; any additional baseline project instructions must be checked before final submission.

Current limitations: one locally configured student account; no account registration or production identity provider; no edit/delete operations; no learning materials; no LLM, RAG, or planning agent yet. Authentication is supporting infrastructure and is not counted as a meaningful feature. Basic authentication is for local development; HTTPS is required for deployment outside localhost. The frontend retains its API credentials in server memory for the signed-in view. A page reload requires sign-in again. No credentials are put in browser localStorage.

3. Implemented design patterns and updated diagrams

The five Stage 1 patterns remain planned, not implemented: Strategy (grading algorithm selection), Observer (calendar synchronization), Facade (AI subsystem boundary), Singleton (shared AIEngine), and Factory (study-resource creation). There is no appropriate reason to force these AI/calendar patterns into deterministic course creation. The final report must replace these status notes with actual source files, roles, methods, and explanations as those features are built. Framework-managed singleton beans alone do not demonstrate the planned AIEngine Singleton.

The implemented architecture adds a Repository abstraction: CourseService depends on CourseRepository; JdbcCourseRepository supplies durable storage without coupling the domain to JDBC. This addresses a real persistence boundary but is additional architecture, not a replacement claim for any of the five course patterns. No new counted pattern is claimed in this increment.

6. Development and verification summary

Verification completed for F01: backend/mvnw.cmd clean verify (followed by verify after correcting BCrypt configuration) passed six tests with zero failures/errors; the frontend production package passed. Backend HTTP integration tests cover successful create/list/read, trimmed text, persistence, field limits, missing/blank values, invalid and reversed dates, same-day courses, invalid JSON, unauthenticated/wrong-password requests, CSRF rejection, and cross-owner isolation. Tests use a separate in-memory database. The real Chrome browser workflow and Java CLI both created courses against an isolated file-backed backend. Both courses survived a real backend restart. GUI checks passed for failed sign-in, cancel, required-field and reversed-date validation, successful creation, refresh, reload/re-authentication, sign-out, backend-unavailable error, and mobile layout without horizontal overflow. Screenshots were visually reviewed. Verification servers use ports 8090/8091, a unique target database, random ephemeral credentials, and are stopped afterward. No submitted video is claimed.

Repeatable runtime checks: scripts/verify-f01.ps1 launches the packaged apps and drives the CLI; scripts/verify-f01-browser.mjs checks the real Vaadin UI. The temporary browser driver is installed under ignored frontend/target/browser-tools; see the root README. Test fixtures live only in ignored target files and are not mixed into the student's database.

Important defect found: the initial BCrypt provider configuration lacked the password encoding ID required by Spring's default delegating encoder. A real HTTP Basic integration test exposed it; adding the {bcrypt} prefix corrected it. The earlier starter was only compiled before UI verification; this increment requires an actual browser workflow and CLI/API checks. No test passwords are production credentials.
